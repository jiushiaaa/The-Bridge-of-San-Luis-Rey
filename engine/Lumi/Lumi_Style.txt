【内容风格】
1、游戏必须有开场情节故事（一般介绍玩家是谁、目标是什么）、中间过场故事或事件（至少一个）、结局情节故事。故事情节的设计应当在符合游戏玩法设计的基础上，尽量融入成熟的故事设计、电影编剧的理论和方案。你需要在游戏玩法设计完成后，进行一些编剧思路调研，并书写故事框架（举例来说，如果是解谜类游戏，则可能需要包含 悬念-误导-反转-真相 等流程；如果是线性的故事，则可能需要包括 引发事件-发展-困境-中间点-伪真相-灵魂黑夜-高潮与解决-结局 等。同一个故事可能有多种写法，游戏系统的独特性也会改变离散式叙事的讲述方案，所以你要选择合适的方案，让这款叙事类游戏充满多变的情节）。
2、玩家（主角）在游戏开始时就应有自己明确的通关目标，在游戏进行过程中需要设法追求达成。目标一般是完成任务、或达到某些数值。通关目标可以不止一种达成方式（如谍战题材时，可以通过"刺杀（武力）"或"买通（金钱）"等不同方式完成任务，都可以通关）。在游戏开头或游戏过程中，可以增加目标。
3、应当设计多个让玩家有记忆点的NPC，且多次登场。NPC对话简单，形象立体但没有角色弧光，行为符合其设定，逻辑自洽。NPC可以用简单的标签来进行标注（如 贪婪的商人、好心的邻居阿姨、精神导师、爱恋对象、对手/仇敌、伙伴、叛徒 等）
4、字数与内容应当“中等丰富”，制作的时候以30-60分钟的中篇游戏长度为宜。用户可阅读到的正文篇幅一般在 20000 到 40000 字。
5、如果游戏中存在地图探索，则必须呈现大地图以表现各地区的连接关系，且需随时在地图上呈现玩家所处的位置。地图地点必须是逐个解锁的（初期只有初始点，解锁一个地方在地图上加入一个新的点）。在玩家前往地图之前，应在地图上简单呈现地图上有什么（如什么角色、什么功能等），便于玩家决策要去什么地方。

【界面风格】
0、以下提到的所有具体游戏系统，都只是用来举例、便于UI设计时理解。实际功能以游戏具体策划为准。
1、浏览器界面分为顶栏（屏幕顶部10%高度）和主区（屏幕90%高度）；主区分为左区（15%）、中心区（65%）、右区（20%）三块。
2、所有重要，需要长期关注的数据，放在顶栏。如会不断变化的能力、维度数值、资源数值、体力等（只是举例）。顶栏别占太高，把空间让给主区。
3、所有需要偶尔查看的项目，陈列在左区。如不常变化的能力值、任务进度或通关要求、资产信息（如拥有的房产或重要角色好感度）等（只是举例）。
4、所有需要在回合内经常查看的项目，放在右区。如为了解谜收集的物品和线索、行为指南（如rouge选择的卡牌或build）、需要处理的工单简报、地图和当前所在位置等（只是举例）。
5、中心区应包含核心玩法，是用户主要查看的区域，承载主要玩法。游戏进行的点击几乎全部集中在这个区域里。你需要将这个区域视为一款文字冒险游戏的主功能区，并假定“只保留中心区，去掉顶栏+左区+右区后（或将顶栏+左区+右区调整为二级菜单后），这个游戏是功能完备、可以玩得下去的”。
6、左区、中心区、右区分别悬浮，且有属于各区自身的滚动条。
7、使用符合项目内容风格的颜色配色。如果项目明确指向某个国家、地区、时代，则需使用有该项目内容代表性的配色方案（可以从该国家的国旗、历史、艺术中选取颜色，并根据作品风格进行调配）。如果有多种颜色风格可选，则优先选择偏明亮的颜色版本。
8、在开篇剧情结束后，必然包含一个弹窗进行游戏玩法说明（新手引导）。
9、游戏中所有需要的图片，你可以使用 "Lumi/Lumi_API_gpt-image2-tencent" 生成。进行生成的时候你应开多threads提高工作效率（最多开10个）。你只能使用low清晰度、1k尺寸的图，jpg格式。此外你也可以使用emoji、有特定样式的文字、填充颜色的图块等作为美术素材（尤其是无法预生成的素材）。
10、界面的有效反馈：所有点击或操作，在界面上均应有有效反馈（如输入数字的话，应该将数字显示出来）；各种弹出型窗口（非流程阻塞型的），都应有可视的“关闭”或“返回”按钮。
11、滚动条常驻：所有具有长内容、可滚动的界面，滚动条默认常驻（且滚动条的宽度很窄，与界面风格优雅融合）。
12、界面任何点击/拖放都必须有可见的交互反馈。反馈即便文案与上次相同，也要可见地重新呈现（重新淡入/打字机效果），不能"看起来没动"。
13、界面常驻一个「提示」入口（只放一处，不重复），任意状态点击都能给出"当前能做什么 / 该去哪"的下一步指引；主线每个卡点都有对应提示，并有永不为空的通用兜底，确保不会"无提示且卡死"。
14、任何图片，不可以使用非等比的拉伸、压缩。默认情况下，图像呈现区的比例，应与图像本身的比例基本一致（避免大面积非等比裁切）。
15、文字字号必须为偶数，不低于12px。根据文字重要度，决定字号（示例：剧情文字16px，重要提示14px，不重要提示或者小字按钮12px）。
16、如果作品中具有AVG或故事呈现的部分，优选以下两种方式之一进行故事呈现：1）类似即时通讯软件的效果，故事逐条累积（旁白居中、对话分左右两侧）；2）类似传统AVG的大图+半透明文字框来呈现剧情（如果是角色的对话，应有角色姓名框）。尽量用类似AVG的旁白+对话驱动的方式，来推动剧情。
17、鼓励使用卡牌方式来做交互：我比较喜欢在主区大的背景图上，用一个个尺寸较大、悬浮在背景图上的卡牌（图片+文字描述+数值描述），来呈现各种功能。如果可能，可以优先选择这种呈现方式（但不用强求，具体仍以游戏实际设计的系统为准）。尽量避免卡牌之间过多互相重叠（尤其是地图上的按钮，应避免热区重叠）。

【文件格式规范】
1、与游戏内容相关的数据（如数值设计、剧情设计、各种字符串），全部保存在 workspace/{game_name}/ 文件夹下（注意game_name文件名应尽量保守，不要有空格或特殊字符）。便于未来支持在 workspace 文件夹下制作多款同类型的换皮游戏。
2、你需要在项目文件夹中保留所有过程文件，但最终游戏数据只保存在 final_game.json 一个文件里。最终游戏引擎只读这一个文件就能获取全部故事、数据。这个文件的数据结构需要“非常干净”，结构合理、没有多余（引擎不需要读）的字段内容。
3、美术资源素材：所有素材保存在 workspace/{game_name}/assets 文件夹下。如果素材中包含了需要多次重复出现的角色/道具，则你需要首先设计“定妆照”（用一套详细的语言来描述该角色/道具），并在未来每次绘制的图像中包含该角色/道具的时候，在prompt尾部声明该角色/道具的特色。游戏要保持统一画风，且不要使用照片风格（日式anime动画风格最佳，画风明亮，京阿尼那种）。
4、根目录下的文件夹和文件包括：
* backend/
* frontend/
* tools/
* workspace/
*  ** {game_name}/  ，其下可以有assets、DEBUG等子文件夹
* README_dev.md
* README_game.md
* run.bat
* 离线游戏.html（快捷方式）
你必须首先在Plan中完全确定整个工程项目的全部文件结构，再开始进行工作。在呼叫sub-agent的时候，必须明确告知文件夹结构和功能。

【技术倾向】
1、在开发过程中：使用 Vite + React + TypeScript 搭建前端工程。界面以真实浏览器 DOM/CSS 渲染为主，不优先使用 Canvas，以便保持文字、按钮、弹层、滚动区域、层级关系等元素可测试、可截图、可维护。
2、游戏逻辑应以“前端状态机 + 数据驱动”的方式实现。与游戏内容相关的数据（如剧情文本、角色、数值、谜题、解锁条件、结局条件、界面文案、素材引用等）最终统一保存到 workspace/{game_name}/final_game.json 这个单一文件。引擎代码只负责解释和渲染数据，不应把具体剧情、谜题答案、大段文案硬编码在组件中。
3、游戏状态应有清晰、可复现的状态模型。推荐使用集中式状态管理或状态机方案管理玩家进度、解锁情况、背包/线索/数值、当前界面、弹层、结局等内容（提到的系统只是举例）。正常游玩流程与测试/调试流程应共用同一套状态模型，避免测试状态与真实游戏逻辑脱节。开发期应提供调试入口或测试路由，可以直接进入任意关键界面与关键游戏状态。不要只依赖从头游玩、逐步点击、逐步解谜来抵达测试画面。每个重要界面、弹层、解锁前后状态、结局状态，都应能通过测试状态直接复现。
4、在开发过程中应配置 Playwright 自动化测试。测试内容至少包括：启动页面无报错、关键界面可打开、按钮和重要文本可见、交互元素未被异常遮挡、主要内容无明显溢出、弹层层级正确、横屏电脑浏览器下截图稳定。对所有关键界面状态建立截图基线，用于发现按钮文字不显示、布局错位、遮挡、主题异常、素材缺失等问题。开发期可以使用本地开发服务器、mock API 或轻量调试服务辅助制作，但最终游戏不应依赖后端运行。
5、开发完成后，必须提供导出工具，将游戏构建为一个不依赖后端、可直接离线运行的纯 HTML 版本，保存在 workspace/{game_name}/index.html。导出版应内联或打包所需的 JavaScript、CSS、final_game.json 数据与必要素材引用，确保玩家只打开该 HTML 文件即可游玩。导出的离线版必须与开发期版本在视觉表现和游戏逻辑上保持一致。

【维护文档规范】项目制作完成后，书写 README_game.md，和 README_dev.md，以便于未来维护：
1、README_game：以完成的游戏作为举例，讲解游戏玩法说明，策划的设计、故事和NPC、游戏流程等。
2、README_dev：游戏的技术说明，前后端文件与主要功能、主要函数等。
这两个文档的要求：必须包含整个游戏的详细说明，包括策划层面和开发层面（你需要说明是如何将策划落地的，有哪些目前的约束等）。总之，你需要做到：未来的AI只需要阅读这两个文件，就可以完全理解整个项目，能对已有的 final_game.json 进行修改和调整，并制作全新的游戏关卡、或使用本游戏模板制作全新不同故事的完整游戏。
如果在自测试的时候调整了游戏玩法数值或技术方案，你需要及时更新这两个文件保持文档最新。不需要书写“历史更新过程”，只需要记录“当前结果”。文档中应包含自维护的要求。

【端口与启动规范】
创建项目时，确定后端使用端口编号 = (月份-1) *31*24 + (日期-1)*24 + 当前小时 + 2001
你需要创建run.bat，简单启动后端，并在浏览器打开对应的前端游戏页面（即游戏的测试版）。
你还需要创建 index.html 的快捷方式，可以快速打开 /workspace/{game_name}/index.html 纯离线版。

【包含自测试的开发风格】
1、在游戏首轮制作完成后，你需要自己试玩一遍游戏，书写游玩log和通关情况（保存在 workspace/{game_name}/Playtest_log.md ），然后直接对功能和策划进行一轮调整，以确保游戏质量更佳。
2、在进行测试的时候你需要确保“人类可解性”，即：1）用人类的逻辑是否能解开所有谜题（所有信息必须已经呈现给用户，且难度应该让普通人类玩家可解）；2）UI应符合人类的习惯和阅读能力（如自动类文字速度应符合人类阅读速度，避免某些关键信息的字藏在角落）等。
